# AltStack launch and migration checklist

Source preparation does not deploy or migrate a live service. Domains were not yet available at the time of this work. Do not merge client-origin changes into automatic production deployments before the new routes are ready.

1. Acquire and verify control of `altstack.io` and `altstack.social`. Attach the actual services in the hosting platform and verify DNS and TLS. Keep old domains serving during migration.
2. Back up Social SQLite, encrypted sessions, encryption/signing keys, object storage, Office files and database, and the PDS repository/blob store. Test restoring into isolated staging. Preserve every DID, user record, recovery code association, and data-encryption key.
3. On a staging Social deployment, set `PUBLIC_ORIGIN=https://altstack.io`. Register the new Turnstile hostname. Review OAuth/MCP client metadata, redirect URIs, consent pages, webhook endpoints, CORS and CSRF origin configuration, app links, mobile associated domains, and external callback URLs. Do not relax origin validation to make migration pass.
4. Configure the PDS endpoint as `PDS_URL=https://altstack.social` only after the service is reachable and its documented hostname migration is complete. Choose `PDS_HANDLE_DOMAIN=altstack.social` for newly issued handles. Existing DIDs, handle DNS records, PLC service endpoints, federation relationships, and repository signatures require protocol-aware migration; a search-and-replace is not an account migration. Resolve representative existing DIDs and handles before and after the change.
5. Test new account creation, existing human sign-in, recovery, browser/native pairing, existing bots, agent keys, OAuth/MCP grants, posts/replies/media, communities, dating privacy, notifications, exports and moderation. Validate Stripe and app-store callbacks in test environments and update public business/support details through their administrative processes.
6. Configure Office `PUBLIC_ORIGIN=https://office.altstack.io`, `SOCIAL_ORIGIN=https://altstack.io`, and the actual editor `DOCS_URL`. Preserve independent signing secrets and persistent volumes. Test creation, upload, sharing, editor JWT/callbacks, save/reopen, revocation and downloads. `ALTSTACK_OFFICE_URL` can override the desktop wrapper origin during staging.
7. Build every native client on its target OS. Verify the supplied logo in installers, taskbars/docks, system menus, startup, dialogs, PWA install surfaces, mobile homescreens, exports and downloaded archives. Validate user settings/keyring continuity. Sign/notarize releases with the owner's identities; no signing credentials were assumed here.
8. Validate the desktop environment, Blender theme, Godot editor theme and splash, creative integrations and permissions on their supported Linux environment. Rebuild generated boot/installer artwork and test real login, boot and install flows. Existing ISO/installer release gates remain open; this rebrand does not complete an operating-system release.
9. Deploy services in dependency order, verify health and actual live behavior, then release clients and publish new links. Use temporary redirects for ordinary old website GET routes after testing. Do not redirect POST, API, PDS/XRPC, authentication, or webhook traffic blindly between origins.
10. Keep rollback snapshots and the previous service origins available until active sessions, external callbacks, installed clients, and account identities have been verified. Revisit repository renames, package IDs, store listings, signing subjects and keyring namespaces as explicit migration tasks.

No DNS, production variables, PDS records, live accounts, billing settings, GitHub repository names or releases are changed by the local review bundle.
